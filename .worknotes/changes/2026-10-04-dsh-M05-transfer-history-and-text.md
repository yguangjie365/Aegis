## 关键决策

| 决策 | 选择 | 理由 | 替代方案 |
|---|---|---|---|
| 剪贴板并发 | 模块内**进程级互斥锁** | 实测：不加锁时并发往返以 `STATUS_HEAP_CORRUPTION` 崩掉测试进程；单进程探针正常 ⇒ 真因是抢 OS 级全局资源 | 依赖调用方串行化（不可控） |
| 交付语义 | **写剪贴板成功 = 交付**（F-FT-34） | 否则发送方看到"已送达"而对端剪贴板空空——两头都无从察觉的谎言 | 回"已写入连接"（更宽松但骗人） |
| 历史老记录 | `#[serde(default)] = File` | 缺字段会让**整份 JSON 解析失败** ⇒ 退化成空历史 ⇒ 用户旧历史被静默丢掉 | 迁移脚本（过度，且老记录确实都是文件） |
| `kind` 是否进 CSV | **不进** | F-FT-58 表头已冻结（8 列），加列即破坏契约 | 加"类型"列（须先改规格） |
| 确认弹窗如何区分类型 | **显式 `PendingKind` 字段** | 让界面从"目录为空且磁盘未知"猜，会在某天因某个合法取值悄悄失效，而这里错不起 | 猜测式判断 |
| 分流实现 | 保留 `receive_file`/`receive_text` 签名，新增 `*_with_first` | 改签名会波及全部调用点（含测试）；`FrameReader` 不预读，新 reader 可从原位置继续 | 泛型穿透 reader/writer（改动面过大） |

## 补记（暂停/恢复端到端实测，2026-10-04）

**方法**：外部探针（另一进程）向应用发 **512 MB**（`sample-huge.bin`）→ 应用接受接收 →
在一个 CDP 脚本里"接受 → 暂停 → 采样两次 → 恢复 → 等终态"，采样取台账的 `transferred`。

**实测输出**：
```
找到任务 t2：已收 2097152 / 536870912
暂停回执={"accepted":true,"state":"active"}
暂停中采样：t0=2097152 → t+2.5s=2097152
✅ 暂停期间已收字节数没有增长（停在块边界）
恢复回执={"accepted":true,"state":"paused"}
任务终态=completed，已收 536870912 / 536870912
```
落盘 536870912 字节，**SHA-256 与源逐字节一致** ✓；探针侧 `Delivered` ✓。

🔴 **最有力的一条**：暂停期间字节数**恰好停在 2097152 = 2 MiB = `DEFAULT_CHUNK_SIZE`** ——
不是"大致停住"，而是**精确停在块边界**，正是 R-14 原文要的语义。
（这也顺带印证了"暂停在每个块之后被检查"这一实现选择。）

**顺带验证到的两件事**：
1. **R-3**：探针首次不带配对码被拒 `PAIRING_INVALID` —— 上一次运行期的免码授权**随服务重启失效** ✓
   符合"免码范围 = 该地址 + 本次运行期"。
2. 暂停/恢复**不影响正确性**：恢复后完整送达、摘要一致。

**尚未验证**：F-FT-25 的"速度 · 剩余 hh:mm:ss"两列（未实现）、"已暂停（对端）"（协议帧未接）、
`PAUSE_TIMEOUT` 的 30 分钟自动取消（等不起，未实测；可按设置调小后补测）。
